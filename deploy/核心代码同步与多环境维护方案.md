# 核心代码同步与多环境维护方案

> 2026-08-30 制定。与《插件同步与多环境维护方案》（插件仓库 `_docs/`）配套：
> 那份管插件，本份管 AstrBot 核心代码的修改、部署与版本升级。

## 〇、给执行 AI 的说明（将本文档交给 AI 执行时必读）

执行环境：公司 Linux 服务器（Docker 部署 AstrBot 容器，容器名 `astrbot`）。

**执行前向用户确认：**
1. `deploy/` 目录已上传到服务器的路径（如 `/home/ymsk/astrbot-bak/deploy`）；
2. 容器内 AstrBot 仓库根路径（通常为 `/AstrBot`，不同则替换脚本中的前缀）。

**禁止事项（遇到异常立即停下询问用户）：**
- 只替换 `deploy/astrbot/` 清单内的文件，不得整目录覆盖容器内的 `astrbot/core`；
- 不得跳过备份直接替换（replace.sh 已内置备份流程，不要手工绕过）；
- 替换后必须重启容器并验证启动日志，再视为完成。

**完成标志：** `replace.sh` 执行成功 + 容器启动日志无异常 +
验证命令（第三节）命中改动标志字符串，向用户汇报。

## 一、网络拓扑与仓库架构

```text
家里 Mac ──── GitHub fork X-85/AstrBot
   │            ├─ company/v4.27.2   生产线（官方 tag v4.27.2 + 生产补丁 + deploy 包）
   │            ├─ dingtalk-feedback-adapter   实验线
   │            └─ master            官方镜像（只快进）
   │                ✕ 与公司内网不通 ✕
公司服务器 ── Docker 容器 astrbot（官方 4.27.2 镜像 + deploy/ 覆盖补丁）
   └─ deploy/ 目录 = 摆渡介质：replace.sh / rollback.sh / check-drift.sh / 载荷 / 本文档
```

要点：
- **核心代码不进公司 GitLab**，公司的"核心副本"就是容器内被覆盖的文件；
- 所有核心改动的唯一事实来源是 `company/v4.27.2` 分支；
- `deploy/astrbot/` 载荷是分支文件的快照，用 `check-drift.sh` 防止两边漂移。

| `company/v4.27.2` | 官方 tag `v4.27.2` (ad4fbfa90) | 生产部署基线，只收生产补丁 |

## 三、日常流程

### 改核心代码（家里）

```bash
# 在 company/v4.27.2 上修改 → 提交 → 推送备份
git add <文件> && git commit -m "feat: ..." && git push origin

# 同步载荷到 deploy 包并校验（必须做，否则公司拿到旧代码）
cp <改动文件> deploy/astrbot/<同路径>/
bash deploy/check-drift.sh        # 输出 [ok] 才算同步完成
git add deploy && git commit -m "chore: refresh deploy payload" && git push origin
```

### 部署到公司容器

1. 携带整个 `deploy/` 目录到公司，上传至服务器（如 `/home/ymsk/astrbot-bak/deploy`）；
2. `sudo bash replace.sh`（自动：备份容器原文件 → docker cp 替换 → 重启容器）；
3. 验证：

```bash
docker logs astrbot --tail 50                    # 启动无异常
docker exec astrbot bash -c 'grep -n "sessionWebhook" \
  /AstrBot/astrbot/core/platform/sources/dingtalk/dingtalk_adapter.py'
```

### 回滚

```bash
cd /home/ymsk/astrbot-bak/deploy && sudo bash rollback.sh
```

### 容器重建后

`docker cp` 写入的是容器可写层，`docker rm -f` 重建后丢失——**重建后必须重跑
`replace.sh`**（脚本会重新备份新容器内的官方原版再替换）。

## 四、公司升级版本（如 4.27.2 → 4.27.4）

```bash
# 家里：
git fetch upstream --tags
git checkout -b company/v4.27.4 v4.27.4
git rebase --onto company/v4.27.4 company/v4.27.2   # 补丁整体搬迁，解冲突
git push -u origin company/v4.27.4
# 重新生成 deploy 载荷（从新分支拷贝清单文件）→ check-drift → 提交
```

然后公司侧：上传新 `deploy/` → `replace.sh` → 插件全部重新上传（或确认兼容）→
五条自检命令全绿。旧分支 `company/v4.27.2` 确认无用后删除。

**基线校验**：容器镜像的构建日期（如 4.27.2-20260805）与 git tag 可能不是同一
commit。升级前先在容器里 diff 一个未打过补丁的原版文件与对应 tag 版本，确认基线
一致；不一致则以容器内实际版本为准找对应 commit。

## 五、实验线 → 生产线

`dingtalk-feedback-adapter` 上成熟的主题，cherry-pick 进生产线：

```bash
git checkout company/v4.27.2
git cherry-pick <commit>     # 注意实验线基于 master，生产线基于 tag，可能需解冲突
```

cherry-pick 进来后：同步载荷到 `deploy/astrbot/` → check-drift → 提交 → 部署。
当前已知遗留：`dingtalk_feedback` 新适配器若要上生产，需连带解决 dashboard
前端不在官方镜像内的问题（私有镜像或前端产物挂载），尚未排期。
